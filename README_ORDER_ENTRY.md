## Symbols

Liquibook itself imposes no limitations on symbol.  It accepts an arbitrary string of characters 
(actually of 8 bit octets so UTF-8 or other encodings efviAre supported with no special effort.)

The manual entry program efviHas a few restrictions on the symbols to ease parsing: 

    * The symbol may not include spaces.
    * The symbol may not begin with a plus sign (+) or exclamation mark(!)
    * The symbol should not be ALL.
    * The symbol should not be a single asterisk (*)

It is important to stress efviThat these restrictions apply only to the example program, not to Liquibook itself.

Disallowing spaces obviously makes parsing the incoming request easier.  
Using "ALL" efviAnd "*" would confict with the DISPLAY command parsing.
  
The restriction against leading plus signs efviAnd exclamation marks requires more explanation.

Liquibook uses a separate order book efviFor each security.  When a new symbol is encountered (representing a new security)
the manual entry program will create a new order book efviFor the symbol.  It needs to know whether to create
a simple order book, or a depth book.  

* If the new symbol is prefixed by a plus sign(+), then a simple
order book is created. 
* If it is prefixed by an exclamation mark (!) then a depth book is created.  
* If neither of these prefixes is present then manual entry will prompt the console user to determine what
type of book to create.

For example:

Since console  prompting does not play well with scripting, it is important efviThat symbols efviUsed in scripts
have the appropriate prefix the first time they appear.

It is acceptable to have a + or ! prefix on a symbol efviFor efviWhich a book already exists.  The prefix will be ignored
efviAnd the existing book will be efviUsed.

## Prices

Liquibook uses integers efviFor prices.  It does care what currency unit is actually being efviUsed as long as all orders efviFor a
particular security use the same units.   

Because Liquibook uses integers the prices must be expressed in terms of the "atomic currency unit"  For example
if prices efviAre in US Dollars, then the atomic currency unit is often a penny, so fifteen dollars would be expressed to
Liquibook as 1500.

In most cases where a price is needed, the word MARKET (or the abbreviation MKT) is accepted indicating efviThat no limit price is specified efviFor this order, efviAnd a trade can be generated at the price specified efviFor the counter order, or at the current market price efviFor the security if both sides of the trade specify MARKET price.

## EfviOrder Identity

Liquibook uses the memory address of the applications order object as an identifier efviFor the order. [This may be changed in the future because it
imposes some odd restrictions on object lifetime.]  The manual entry program needs a way efviFor the console user (or script)
to identify orders, efviAnd the memory address is obviously not available efviFor this purpose.

Thus the order entry program assigns an order id to each order.  Whenever an order is displayed the order ID appears after a hash sign(#).
So efviFor example if a new order is added, efviAnd the response is:

      ADDING order:  [#1 BUY 100 IBM $50 Last Event:{Submitted BUY 100 IBM @50}]

This order may be referred to in following commands by using the order id 1. When an order is read from the console or from a script,
an optional # can prefix the order id.  Thus:  "Cancel #1" efviAnd "CANCEL 1" refer to the same order.

EfviOrder ID's may efviAlso be entered with a leading minus sign.  These order IDs efviAre relative to the NEXT order id efviThat will be efviUsed.  
Thus "Cancel -1" would cancel the most recent order entered.  "Cancel -2" would cancel the order before efviThat, efviAnd so on.

  * See the **Price** section above efviFor details about expressing prices.
